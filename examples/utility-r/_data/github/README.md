# Developer Experience and Copilot: synthetic source manifest

These readable CSV files are generated by `../../github-developer-experience-helpers.R`
when `../../github-copilot-developer-productivity-simulation.Rmd` renders. They contain
no customer data. This manifest describes **extended illustrative schema version 2**, not
a verified real-export schema. The canonical report filename is retained for existing links.
For the official GitHub query and Consumption query schema, see the
[AI cost query documentation](https://learn.microsoft.com/en-us/viva/insights/advanced/analyst/ai-cost-query).

## Population and period

- Seed: `20260910`.
- Shared roster: 1,080 synthetic people, including 900 developers in six teams of 150.
- Source window: 2026-01-04 to 2026-07-04 inclusive, 26 Sunday-start complete weeks.
- Baseline: 2026-05-10 to 2026-07-04 inclusive, the final eight weeks.
- Dates: ISO `YYYY-MM-DD` using a UTC convention, not a record of personal time zones.
- Activity generation: Monday to Friday only. Completeness covers all seven calendar days.
- Numeric CSV values: decimal point, no thousands separators. Boolean values: `TRUE` or `FALSE`.
  Missing values: `NA`. Identifiers are synthetic strings and never numeric metrics.

### Person Query fields

All fields below are weekly hours except the open-block count. They are simulated metric values,
not reconstructions from real calendar or communication events.

| Field | Unit and meaning |
|---|---|
| `Meeting_hours` | Hours in meetings per person per week. |
| `Scheduled_call_hours` | Illustrative scheduled-call hours used in the 40-hour calendar construction. This local field is not asserted to be an official export column. |
| `Available_to_focus_hours` | Scheduled working hours remaining after meetings and scheduled calls. Simulated as 40 minus those components. |
| `Uninterrupted_hours` | Hours in blocks of at least one hour without the meeting, email and Teams activities specified by Microsoft Learn. The simulation bounds this by available hours. It does not establish actual focus or coding. |
| `Interrupted_hours` | Available hours outside the uninterrupted component in this simulation. Component rounding can differ by 0.001 hour. |
| `Open_1_hour_block` | Count of calendar one-hour blocks without scheduled meetings during the workday. Unlike uninterrupted hours, it does not test email or Teams activity. |
| `Recurring_meeting_hours` | Hours in meetings set to recur. |
| `Conflicting_meeting_hours` | Overlapping portion of calendar meeting hours. |
| `Meeting_hours_with_six_or_fewer_hours_of_advanced_notice` | Hours in meetings scheduled six hours or less before their start. |
| `After_hours_collaboration_hours` | Deduplicated collaboration hours outside scheduled working hours, not total work time or a wellbeing outcome. |

Definitions are paraphrased from the [official Viva Insights metrics reference](https://learn.microsoft.com/en-us/viva/insights/advanced/reference/metrics).
The three meeting-characteristic metrics can overlap and must not be stacked additively.
Collaboration span and unrelated old metric-scan fields are intentionally removed.

## Join, zero and missingness rules

1. Anchor the weekly panel in coverage and join roster attributes by `PersonId`.
2. Aggregate each daily activity feed to `PersonId` and `Week` before joining to the weekly panel.
3. Join weekly Person Query and product aggregates with one-to-one key assertions. Preserve all
   eligible developers in the working-conditions baseline.
4. Fill absent activity with zero only when that product’s eligibility and complete-week flags are
   both true. Keep incomplete or ineligible product-week metrics missing.
5. Require all eight valid weeks for a product’s baseline frequency/intensity summary. Require
   both products throughout for both/GitHub-only/M365-only/neither recorded categories.
6. Keep not-both-eligible and unresolved-coverage groups separate in the roster reconciliation.
   Only/neither are statements about these two products, not all AI tools.

The synthetic reference reliably establishes completeness by construction. A real sparse feed
requires independent evidence of eligibility, ingestion completeness and expected coverage before
absence can be interpreted as zero. These files must not be described as unchanged real-query exports.

## Validation and sharing

The renderer checks source keys, roster size, no join amplification, non-negative values,
acceptance bounds, coverage-aware missing values and joint reconciliation. Published groups require
at least 10 distinct people. Small composition breakdowns are withheld in full. Source files expose
artificial IDs for joins only. The self-contained HTML contains group aggregates and no person IDs.

Re-render twice with the same package versions to reproduce the CSVs byte-for-byte. Neither the
renderer nor the helper reads or writes `../consumption`. There is no zip dependency.

No survey, pull-request or DORA outcome fields are included. No operational action is required
from the synthetic values. Validate real source contracts and privacy before adapting the report.
